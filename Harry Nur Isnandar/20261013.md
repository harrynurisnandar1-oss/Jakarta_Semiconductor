### Core Data Structures & Signatures

* **COSEM Snapshot & Model ([`ami_cosem_model.h`])**
  * `AmiCosemRegisterSnapshot`: Source data structure (RAM/FRAM) containing instantaneous register arrays, RTC, and `event_log[]` / `billing_history[]` ring buffers.
  * `AmiCosemProfileSelection`: Filter parameters for *Selective Access* (Selector 1: Date-time range; Selector 2: Entry index range).
  * `ami_cosem_register_read_selected(...)`: Object data read function generating A-XDR byte-streams.

* **DLMS Association ([`ami_dlms_association.h`])**
  * `AmiDlmsAssociation`: Holds session state, selected authentication mechanisms, and HLS challenges.
  * `ami_dlms_process_aarq_with_security(...)`: Validates AARQ and builds AARE responses.
  * `ami_dlms_process_hls_reply(...)`: Validates GMAC client proof and generates server proof.

* **APDU Dispatcher ([`ami_dlms_apdu.h`])**
  * `ami_dlms_process_get_request(...)`: Plaintext APDU read parser (LLS / No-Auth).
  * `ami_dlms_process_ciphered_request(...)`: Encrypted APDU parser (`Glo-Get`/`Glo-Action` for HLS).

#### Rationalization for Host Simulator (`gurux_simulator.exe`):
On physical meters, Gurux (or actual HES) communicates via optical probes, RS-485 serial cables, or cellular 4G/NB-IoT modems.

As the physical hardware board (STM32U585 PCB) is pending arrival, `gurux_simulator.exe` was implemented to wrap the complete meter firmware logic into a local TCP socket (Port 4059). This enables Gurux DLMSDirector to test and read from the system as if communicating with a physical 3-phase smart meter deployed in the field.
